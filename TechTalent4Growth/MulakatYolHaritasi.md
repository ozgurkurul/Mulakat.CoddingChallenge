#### ❓ Soru 4: *"What happens when a customer successfully pays on the webshop, but the ERP (NetSuite) is temporarily unavailable?"*
*(Müşteri webshop'ta ödemeyi başarıyla yaptı ama o sırada ERP geçici olarak çöktü / ulaşılamıyor. Ne olur / bunu nasıl tasarlarsın?)*

**🎤 İngilizce Cevap:**
> *"In a modern e-commerce platform, a customer's checkout experience should **never** fail or hang just because a downstream system like the ERP is temporarily down or slow.*
>
> *I solve this by decoupling the systems **asynchronously** using the **Outbox Pattern and a Message Broker** (such as Azure Service Bus, RabbitMQ, or Kafka).*
>
> *Once the payment succeeds and the order is created in BigCommerce, our .NET integration layer immediately acknowledges the order and stores an `OrderPaid` event in a persistent queue or database outbox. A background worker then picks up that message and tries to push it to NetSuite.*
>
> *If NetSuite is unavailable or returns a `503` or `429 Rate Limit`, the worker applies **exponential backoff retries**. If the ERP stays down for a longer period or rejects the payload due to a data issue, the message moves to a **Dead-Letter Queue (DLQ)**, triggers an alert for the engineering team, and can be safely replayed as soon as the ERP is back online. Zero orders are lost, and the customer never notices a problem."*

---

#### ❓ Soru 5: *"How do you prevent the same order or payment from being processed twice when messages are retried or duplicated?"*
*(Mesajlar tekrar denendiğinde veya çift geldiğinde aynı siparişin iki kez işlenmesini nasıl önlersin?)*

**🎤 İngilizce Cevap:**
> *"Because message brokers and webhooks usually work on an **at-least-once delivery** model, duplicate messages are guaranteed to happen in production. The key solution here is **Idempotency**.*
>
> *In the .NET integration layer, every incoming event or webhook must carry a unique deterministic identifier—such as an `Idempotency-Key`, `ExternalOrderId`, or `EventId`.*
>
> *Before processing any message, our service checks an **Inbox / Processed Messages table** in PostgreSQL (backed by a unique database constraint). If that ID is already processed or currently in progress, we safely ignore the duplicate and return a success status. Furthermore, when pushing data to external systems like NetSuite, we include our unique reference ID so the ERP also treats repeated requests idempotently."*

---

#### ❓ Soru 6: *"What happens when inventory/stock changes simultaneously in the ERP, the webshop (BigCommerce), and external marketplaces (Channable)?"*
*(Stok aynı anda hem ERP'de, hem webshop'ta hem de pazaryerlerinde değişirse ne olur? Overselling'i nasıl önlersin?)*

**🎤 İngilizce Cevap:**
> *"This is a classic omnichannel challenge that I dealt with at DeFacto and Yemeksepeti. To solve it, we need three principles:*
>
> *First, **Single Source of Truth**: Usually, the ERP or Warehouse system (NetSuite) is the ultimate master of physical stock, while the integration layer tracks **active reservations** for orders that are placed but not yet synced to the ERP.*
>
> *Second, **Event-Driven Delta Updates & Optimistic Concurrency**: Instead of overwriting stock blindly with slow batch jobs, stock changes should flow as ordered events per SKU, using version numbers or timestamps so an older message never overwrites a newer stock level.*
>
> *Third, **Safety Buffers for Marketplaces**: When pushing stock to external channels via Channable, it's good practice to expose 'Available to Sell' stock—which is physical stock minus active reservations—and keep a small safety buffer for fast-moving items so two channels don't sell the very last item at the exact same millisecond."*

---

#### ❓ Soru 7: *"How do you recover when one part of a multi-system process fails, and how do you make sure issues are identified quickly?"*
*(Çoklu sistem sürecinin bir parçası hata verdiğinde nasıl kurtarırsın ve sorunların hızla fark edilmesini nasıl sağlarsın?)*

**🎤 İngilizce Cevap:**
> *"First, you can't fix what you can't see—so **Observability** is critical. Every order or data flow across BigCommerce, the .NET integration layer, and NetSuite should carry a **Correlation ID (Trace ID)** in structured logs. That way, if something fails, we can trace the entire journey of a single order across all systems in seconds.*
>
> *Second, we distinguish between **transient errors** (like a network timeout, which is recovered automatically via retries) and **business/validation errors** (like a missing tax code or invalid SKU in the ERP). Business errors shouldn't be retried endlessly; they go straight to a **Dead-Letter Queue** and trigger a proactive alert in Slack or Teams.*
>
> *Third, for multi-step workflows, we use **Saga patterns / compensating actions** and periodic **reconciliation jobs** that compare totals between the webshop and the ERP to catch any silent discrepancies early."*
